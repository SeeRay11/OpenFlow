## A. What omp is
- Compiled/bun CLI `omp` v18.12.2 (`/usr/local/bin/omp`; package `@oh-my-pi/pi-coding-agent` under `/root/.local/share/reflex/bun/install/global/node_modules/@oh-my-pi/`, `bin: dist/cli.js`; `package.json:3,578-579` engines `bun >=1.3.14`; box has bun 1.4.0). It is a per-process agent (TUI default; `--mode text|json|rpc|rpc-ui`, `-p`, `acp`). It is also an SDK (omp://sdk.md) and has bundled RPC clients (TS `modes/rpc/rpc-client.ts`, `rpc-frame.ts`; Python/Rust/Go). There is NO daemon. The only long-lived pieces are optional: auth-broker, auth-gateway, and the prediction daemon.
- State, default profile (`omp config path` → `/root/.omp/agent`): `config.yml` (settings), `models.yml` (custom providers, apiKey refs), `agent.db` (credential store, plus legacy settings), `models.db` (model catalog cache), `.env` (provider env), `sessions/<encoded-cwd>/<ts>_<sessionId>.jsonl` (omp://session.md:42), `terminal-sessions/`, `blobs/`, `agents/`, `mcp.json`, `lsp.json`. Session-owner leases are in `~/.omp/run/session-owners` (session.md:540). Overrides: `PI_CODING_AGENT_DIR` (default profile only), `PI_CONFIG_DIR`, `--profile <n>`/`OMP_PROFILE` (→ `~/.omp/profiles/<n>/agent`), `--config <overlay.yml>` (repeatable), `PI_CONFIG_FILES`. Project config is `<cwd>/.omp/`. `.env` precedence is process env > project `.env` > agent `.env` > `~/.omp/.env` > `~/.env`.
- Pin/verify: `omp --version` → `omp/18.12.2` (about 0.75s). `get_state` has no version field. [INFERENCE] The host should run `omp --version` once at startup and compare it against a pinned range. The ready frame carries `supportedProtocolVersions:[1,2]`.

## B. Startup recipe (every flag below appears in `omp --help`)
```
omp --mode rpc --no-ui --no-session|--session-dir <dir> --no-title --no-extensions -e <swarm-ext> \
    --no-skills --no-rules --no-lsp --no-pty --cwd <dir> --model <prov/id> --thinking <lvl> \
    --tools read,grep,glob,edit,write,bash,... --append-system-prompt <text|file> \
    --approval-mode always-ask|write|yolo --max-time <10m> [--config overlay.yml] [--profile <n>]
```
- Also present: `--no-tools`, `--api-key` (runtime, never persisted), `--system-prompt`, `--add-dir`, `--auto-approve`/`--yolo` (forces yolo; beats `--approval-mode`), `--advisor`, `--smol/--slow/--plan`, `-c/-r/--restore`, `--hook`.
- RPC mode already sets `PI_NO_TITLE=1`; `--no-title` is harmless. `rpc-ui` also sets `PI_NO_PTY=1`. `@file` args are rejected in RPC mode.
- Per-card persistence: either `--no-session`, or `--session-dir <host-keyed dir>`, which survives restarts via `open_session{sessionDir,provider?,modelId?}`. `open_session` fails under `--no-session`.
- Mode choice: `rpc` + `--no-ui` emits no UI frames except a host-issued login. Without `--no-ui` I observed an unsolicited `extension_ui_request` with `widgetKey` right after ready, which is presentation noise (G). Use `--mode rpc-ui` when the host must answer approval/`ask` dialogs, plus `--no-ui` if extensions should stay headless (rpc.md:1200-1212).
- Use `--cwd` rather than the spawn cwd. Pass `env` explicitly: it is inherited, and `PI_CODING_AGENT_DIR`/`--profile` isolate state per host.

## C. Protocol facts
- Framing is JSONL on stdio, not JSON-RPC. A ready frame is written first: `{"type":"ready","protocolVersion":1,"supportedProtocolVersions":[1,2],"maxFrameBytes":1048576,"maxReassembledFrameBytes":67108864}`.
- **negotiate_protocol v2 is worth using.** Without it, any frame over 1 MiB fails (responses) or gets elided (events). I observed `get_available_models` (738 models) arrive as 8 `rpc_chunk` frames after negotiating. Chunk shape: `{type:"rpc_chunk",chunkId,index,count,byteLength,data:<base64 utf8 json slice>}`. The reader must concatenate by index and `JSON.parse` the result. Inbound frames are never chunked. For an oversized `agent_end`, leading messages already streamed are dropped and `messageCount` is added, so retain streamed `message_end` frames (rpc.md:62-66).
- Correlation: every command takes `id?`. Responses are `{id,type:"response",command,success,data?|error,code?}`. `bash`, `prompt` and `predict_word` responses can arrive out of order, so match on `id`. An unknown command returns `success:false,error:"Unknown command: nope"`. Malformed JSON gives a `command:"parse"` failure and the loop continues.
- `prompt{id,message,images?,streamingBehavior?:"steer"|"followUp"}`: the response `success:true` means admitted, not finished. Completion is exactly one of two things. Either the response has `data.agentInvoked:false` (local slash commands; no `prompt_result` follows), or a later frame `{type:"prompt_result",id,agentInvoked:true,status:"completed"|"aborted"|"error",error?:{message,provider?,model?,httpStatus?,retryable},sessionSettled}` arrives. Prompting while streaming without `streamingBehavior` fails.
- `agent_end{messages,isTerminal?,yielded?,awaitingAsyncWork?}`. `yielded:true` means the agent finished its turn. It is false while retrying, compacting, or answering a stop-time reminder. `session_settled` (separate frame) is written once nothing can wake the session: no run, no queue, no background bash/task/eval. `get_state.isSettled` and `hasPendingAsyncWork` give the same answer. Rule: present the answer on `prompt_result`; treat the card as finished only on `session_settled`. A provider failure is a normal `agent_end` whose last assistant message has `stopReason:"error"`, with `prompt_result.status:"error"`; the command is still `success:true`.
- `abort` stops the turn (stranded steers are requeued and drained into a fresh turn). `abort_and_restore_queue` returns `{steering:[{text}],followUp:[...]}`. `abort_and_prompt` aborts, then prompts (it waits for the abort). `steer` / `follow_up` queue messages. `queue_update{steering:[str],followUp:[str]}` is an event. `remove_queued_message` and `promote_queued_message` exist.
- `get_state` returned: `model{provider,id,...full Model}`, `thinkingLevel`, `isStreaming`, `isCompacting`, `steeringMode`, `followUpMode`, `interruptMode`, `sessionId`, `sessionFile?`, `autoCompactionEnabled`, `queuedMessageCount`, `queuedMessages{steering,followUp,liveSteered}`, `hasPendingAsyncWork`, `isSettled`, `todoPhases`, `fast/slowMode*`, `messageCount`, `contextUsage{tokens,contextWindow,percent}`, `goal`, plus `systemPrompt[]` and `dumpTools[]`. The system prompt ran ~96k+27k characters and the tool schemas ~12 tools, so `get_state` is large (chunked under v2). Do not poll it.
- `get_messages` is legacy and monolithic. `get_messages_page{cursor?,limit 1-256}` returns `{messages,totalMessages,nextCursor?}`. It fails with `code:"session_busy"` while streaming or compacting, and with `code:"stale_cursor"` when the snapshot changed. `get_entries{since?}` returns `{entries,leafId}` from the append history (unknown `since` fails with `code:"unknown_since"`). `get_tree` returns `{tree,leafId}`.
- `set_event_filter{events:string[]|null,messageUpdates?:"full"|"delta"}` echoes `{events,messageUpdates}`. It filters session events only. Responses, `prompt_result`, `session_settled`, UI requests, `notice` for persistence and subagent frames are never filtered. Each call replaces the whole state. With `messageUpdates:"delta"`, `message_update` becomes `{type,messageId,message:{role},assistantMessageEvent{type,delta,contentIndex}}` with no `partial`. This is the cheap mode for the engine.
- `set_subagent_subscription{level:"off"|"progress"|"events"}` (default off) gates the frames `subagent_lifecycle`, `subagent_progress` and `subagent_event`. Related commands: `get_subagents`, `cancel_subagent`, `steer_subagent`, `get_subagent_messages`. Verified: the `off` level was accepted. `set_auto_retry{enabled}` returns no data. `abort_retry` also exists.
- Exit: closing stdin rejects pending UI and host-tool requests, drains accepted commands, disposes the session, flushes stdout, and exits 0. It exits 1 if a session-persistence failure is still latched. The client MUST keep reading stdout after closing stdin. Verified exit codes were 0 in both probes. stderr was empty in both probes and is only a mirror for persistence notices (rpc.md:1500-1507). Process death of the parent also closes the pipe (G).

## D. Event mapping (omp → opencode-style surface)
Verified from types `pi-agent-core/dist/types/types.d.ts:1114-1160` and `pi-ai types.d.ts:1014-1095,1379-1439`. Message `usage` is `{input,output,cacheRead,cacheWrite,totalTokens,cost{input,output,cacheRead,cacheWrite,total}}` (omp://session.md:150-164). Roles are camelCase: `user`, `assistant`, `toolResult`.

| omp frame | opencode-style surface |
|---|---|
| `agent_start` | status `busy` |
| `prompt_result` completed/aborted/error plus `session_settled` | status `idle`, with `prompt_result.status` giving success/aborted/error; error → session error |
| `message_start` (`messageId`) | new message id |
| `message_update` with `assistantMessageEvent.type:"text_delta"{contentIndex,delta}` | text part delta, keyed by `messageId`+`contentIndex` |
| `thinking_delta{delta}` | reasoning part delta |
| `toolcall_delta` / `toolcall_end{toolCall{id,name,arguments}}` | tool part `pending` (args streaming) |
| `message_end{message}` where `role:"assistant"` | finalize text parts; **step-finish**: tokens `{input,output,reasoning?,cache{read:cacheRead,write:cacheWrite}}`; cost `usage.cost.total`; `stopReason` stop/length/toolUse/error/aborted |
| `tool_execution_start{toolCallId,toolName,args,intent?}` | tool `running` |
| `tool_execution_update{partialResult}` | tool metadata/output update (`tool_stream_update` is an extra stream) |
| `tool_execution_end{result,isError?}` | tool `completed` / `error` (the `toolResult` message holds `content[]`,`details`,`isError`) |
| `turn_end{message,toolResults}` | step boundary |
| `auto_retry_start{attempt,maxAttempts,delayMs,errorMessage,errorId?}` / `auto_retry_end{success,attempt,finalError?}` | session status `retry` (attempt/next=delayMs/message) |
| `auto_compaction_*`, `retry_fallback_*`, `model_changed` | informational |
| `notice{level,message,source?}` | toast/log |
| `agent_end` with `isTerminal:false` or `yielded:false` | still busy |

- **Errors**: the assistant message carries `stopReason:"error"`, `errorMessage`, `errorStatus` (HTTP status), `errorId` (bit-packed classifier) and `errorClassificationMessage`. `prompt_result.error{message,provider?,model?,httpStatus?,retryable}` comes only after omp's own automatic retries are exhausted (`retry.*` settings; non-compaction-retry-policy.md). The engine's classifier should key on `httpStatus` (429/5xx/408 → retryable) and `retryable`, and fall back to message text. Context overflow is compaction, not retry. Failures at the command level are `success:false` plus `error` text (e.g. `Model not found: <provider>/<modelId>` from `set_model`/`open_session`). [INFERENCE] I did not trigger live 429/auth-missing errors because that needs a model call.

## E. Approvals and questions
- `--approval-mode always-ask|write|yolo` (default `yolo` in schema, verified by `omp config get tools.approvalMode`). Tiers are read/write/exec. `always-ask` prompts for write and exec; `write` prompts only for exec. Per-tool overrides use `tools.approval.<tool>: allow|deny|prompt`. A tool or user `deny` always wins. Subagents always run headless yolo.
- Approval prompts go through the extension runner as an `extension_ui_request` with `method:"select"`. Evidence: `src/tools/approval.ts:515-522`. `title`/`message` text is the prompt: first line `Allow tool: <name>`, optionally `Reason:` and details. Options are `["Approve","Approve <subject> for this session","Deny"]`; the session option is offered only when the mode raised the prompt. Answer with `{type:"extension_ui_response",id,value:"Approve"}` (once), the exact session label (always-for-session), or `"Deny"` (reject). Cancel, timeout or any other value is deny. [INFERENCE] The field carrying the prompt text in the frame (`title` vs `message`) was not captured live.
- Under `--no-ui`, approval-requiring tools fail closed with a no-interactive-UI error, with no dialog. So the host must run `rpc-ui` for manual-policy cards.
- Defaults: manual permission policy → `--mode rpc-ui --approval-mode always-ask` (or `write` to cut noise). Auto policy → `--approval-mode yolo`, or `--auto-approve`, with `--no-ui`. [INFERENCE] These choices are my mapping, not from the docs.
- `ask`: send `set_ask_dialog{enabled:true}` (verified `{"enabled":true}` in rpc-ui). Then `extension_ui_request{method:"ask",id,questions:[{id,question,header?,options:[{label,description?,preview?}],multi?,recommended?}],timeout?}`. Answer: `{type:"extension_ui_response",id,answers:[{id,selectedOptions:[labels],customInput?}]}`, one entry per question in order. Timeout or cancel (`cancelled:true,timedOut?`) picks recommended or first. Without the opt-in, `ask` falls back to `select` plus `editor`. Other responses: `{value}`, `{confirmed}` (for `confirm`), `{cancelled:true}`. `cancel{targetId}` closes a dialog. The `select` request may carry `optionDetails`.
- Host-answerable methods: `select, confirm, input, editor, ask`. Fire-and-forget: `notify, setStatus, setWidget, setTitle, set_editor_text, open_url{url,launchUrl?,instructions?}`.

## F. Models, auth, config discovery
- `get_available_models` → `{models:[Model]}`, 738 models over 8 providers (anthropic, openai-codex, openrouter, xai-oauth, zai, cursor, muse-code, anthropic-api); anthropic had 28. `Model` keys: `id,name,api,provider,baseUrl,reasoning,input:["text","image"],cost{input,output,cacheRead,cacheWrite}` (USD per million tokens), `contextWindow,maxTokens,identity{class,family,revision},thinking{mode,efforts[],...},compat{...},tokenizer,promptCache{short,long}`. It waits for background discovery and is chunked under v2. It took 3.1s here, and 2.8s to arrive in the earlier run.
- `get_available_thinking_levels` → `{levels}`. `set_model{provider,modelId}`, `set_thinking_level{level}`; levels are `inherit|off|minimal|low|medium|high|xhigh|max`.
- `get_login_providers` → `{providers:[{id,name,available,authenticated}]}`: 84 providers. `login{providerId}` emits `open_url` frames (plus non-secret `input` prompts after the URL). Secret prompts are rejected with an error that points to the terminal. `get_logout_accounts{providerId}` → `{accounts:[{credentialId,provider,label,detail,type,active}]}`. `logout{providerId,credentialId}` → `{remainingSource?}`. `label`/`detail` contain account emails, so redact them in UI logs.
- Key resolution order (providers.md:55-61): `--api-key` > `models.yml` apiKey > stored OAuth > login-saved key > extension config fallback > provider env var (incl. `.env`) > other stored key. A host can store a key by: (a) env var in the child env or in `~/.omp/agent/.env`; (b) `models.yml` `providers.<id>.apiKey: ENV_NAME` or `"!cmd"` (stdout read, 10s timeout); (c) `omp auth import <file>` (JSON `{credentials}` as exported by `omp auth export`, so also a possible write path); (d) the RPC `login` flow (OAuth or non-secret key flows only). Secret key entry has no RPC path, so the settings UI must write env/`models.yml` or use the PTY terminal.
- Settings schema from real data: `omp config list --json` → object of 557 keys `{ "<dotted.key>": {type, description, value, redacted?} }`. Types: boolean 220, number 139, enum 98, string 54, array 28, record 18. `omp config get <key> --json`, `set`, `reset`, `path`, `init-xdg`. The JSON has no enum choice list or group; the text `omp config list` groups by `[category]` and shows `(a|b|c)` enum values inline, so parse that for enum options and categories [INFERENCE: or read `config/registry.ts` in the package src]. Writes go to `config.yml`; long-lived RPC processes watch on-disk config. Relevant keys: `tools.approvalMode`, `tools.approval`, `retry.*`, `modelRoles`, `enabledProviders`, `disabledProviders`. `omp models --json` plus `omp models refresh` / `find` give the catalog offline. Session-only overrides come through RPC (`set_auto_retry`, `set_auto_compaction`, `set_steering_mode`, ...), which do not write `config.yml`.
- Auth broker/gateway (`omp auth-broker`, `OMP_AUTH_BROKER_URL`/`_TOKEN`, `auth.broker.url`) is an optional shared credential vault. Env vars override. See auth-broker-gateway.md.

## H. Risks
- Process tree: each card runs a bun child that also spawns tool shells, MCP servers and LSP (disabled via `--no-lsp`), browser, and Python. [INFERENCE] Start the child in its own process group and kill the group on card delete. Keep stdout drained after stdin close; a stalled pipe delays exit indefinitely (rpc.md:75-77). `--max-time` bounds a runaway session. Exit on stdin EOF held in both probes, including parent death, so the host can rely on EOF-based shutdown, with a SIGKILL timeout for background `bash`/`task` work (`session_settled` waits for it).
- Startup cost: ready arrives in about 1.6–2.2s per process, so a pool of pre-spawned processes plus `open_session` can hide it (`open_session` rebinds a process to a session dir).
- Output size: `get_state`, `get_available_models` and `agent_end` can exceed 1 MiB, so v2 negotiation plus a chunk reassembler is mandatory (or use `RpcFrameDecoder` from the package). Use `messageUpdates:"delta"` to avoid full `partial` snapshots per token.
- Concurrency: two processes writing the same session file get a lease conflict and one silently forks to a sibling file (session.md:541), so give each card its own `--session-dir`. Concurrent `agent.db` access across many processes is SQLite WAL, which is probably fine but not verified.
- Version drift: the protocol is custom and OMP-native (not Pi-wire identical; `omp_rpc` wire schema is generated via `bun run gen:rpc` into `rpc-wire.schema.json`). Closed enums fail the frame on unknown values; the host should ignore unknown event types, filter with `set_event_filter`, and pin `omp` ≥18.12.2 <next-minor. Unknown event names are accepted without error by the filter. `omp update` self-updates the binary, so disable or manage it. Auth state is shared at `~/.omp/agent/agent.db` across all omp usage on the machine; use `--profile`/`PI_CODING_AGENT_DIR` to isolate the app's runs.
- Config surface is large (557 keys, enum values not in the JSON), so the settings UI must use curated or generated hints.
