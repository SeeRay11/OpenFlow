## G. Risks
1. `engine.ts` runs in the browser and holds callbacks (permission/question promises) in module state; moving to host-owned Omp RPC changes who resolves them — SSE-like transport to browser needed; reload mid-run loses resolvers (existing resume path keys on `sessionID`).
2. Per-node tool restriction relied on generated opencode agents + `opencode.json` merge; Omp needs per-process tool flags/extension config, otherwise `unrestricted-write` safety property disappears silently.
3. prompt.ts tells cards "you share no memory" (640-643) — contradicts substrate memory; must be rewritten along with uplift so briefing is not itself uplifted twice.
4. Uplift failure confirmation must not deadlock the run when parallel cards fail simultaneously (modal is one-at-a-time, like questions) and must settle on Stop (`rejectQuestions` analog).
5. No dialog a11y baseline; adding a PTY terminal that captures keys conflicts with global shortcuts (Ctrl/Cmd+Z undo in state, Esc handlers, Enter on the task input).
6. Secrets: never render Omp env/keys; the current `envPresent` returns names only — keep that rule.
7. Stale copy/labels in ~15 places ("opencode serve", "restart the engine"), plus `CHANGELOG`/FLOW.md rules; `.oc-*` class names can stay.
